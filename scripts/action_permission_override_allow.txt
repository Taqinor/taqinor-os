#
# CE QUE CETTE LISTE EST. Le sweep bis d'AUD403 a rejoué ACTION PAR ACTION la
# trentaine de classes combinant un `get_permissions()` local à branchement sur
# `self.action` et une `@action(permission_classes=...)` inline. Verdict :
# AUCUN cas où le repli était PLUS FAIBLE que la permission inline voulue —
# seul `ventes/views/devis.py` l'était, et il est corrigé. Ces classes sont
# donc VÉRIFIÉES BÉNIGNES : leur repli est égal ou PLUS STRICT que la
# déclaration de l'action. La consigne du plan est explicite : « ne pas
# re-auditer, seulement geler le résultat par une garde CI ».
#
# CE QUE CETTE LISTE N'EST PAS. Un blanc-seing. La garde reste un CLIQUET :
# toute classe NOUVELLE — ou toute nouvelle `@action(permission_classes=...)`
# ajoutée à une classe listée dont le nom n'est pas nommé par le branchement —
# échoue tant qu'elle n'a pas, elle, été vérifiée action par action. Ajouter
# une ligne ici est un choix explicite, revu comme du code.
#
# À SAVOIR (relevé en construisant la garde, hors périmètre de correction) :
# `devis.py::DevisViewSet.composition` déclare `IsResponsableOrAdmin` alors que
# le repli atteint vaut `IsAdminRole` — donc PLUS STRICT, pas plus faible (ce
# n'est pas le défaut AUD403), mais la déclaration inline ment dans l'autre
# sens : un rôle « responsable » est refusé là où l'@action dit l'autoriser.
# À trancher par une tâche dédiée, jamais par un élargissement de garde.
#
