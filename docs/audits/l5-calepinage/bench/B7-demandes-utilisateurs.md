## 0. Honnêteté sur les sources (lire d'abord)

**Ce qui a donné du volume.** Les tableaux d'idées des éditeurs de conception (OpenSolar, Aurora, PVcase, Solargraf, Pylon, Reonic, SolarEdge, Enphase, Victron) sont fermés, privés ou introuvables ; les sites d'avis ne montrent presque aucun texte d'utilisateur pour les outils PV. Le volume vient donc de quatre sources qui répondent normalement : l'API publique GitHub, l'API publique de Stack Exchange, le flux public d'avis de l'App Store (iTunes RSS) et un fil de feuille de route d'un éditeur (Photonik). Cela fausse la représentation : les demandes viennent surtout de **développeurs de bibliothèques de simulation** (pvlib, SAM, PVMismatch…), d'**installateurs mobiles** (avis d'applications de mise en service) et de **bricoleurs** (Stack Exchange), pas de bureaux d'études qui utilisent PVsyst ou PV*SOL au quotidien (ceux-là sont dans B1, B4, B5).

**Limites de lecture à retenir.** (1) Les votes GitHub sont presque tous 0 : l'engagement se lit plutôt dans les commentaires (affichés). (2) Les lignes marquées **(*)** (avis d'applications iOS hors OpenSolar/Mapper/Scanifly) reçoivent un libellé générique par grappe (scan, connexion, lenteur…) choisi par mots-clés dans l'avis ; le titre de l'avis en crochets est le seul détail propre à la ligne ; l'échantillon a été trié par longueur de texte (les avis longs d'abord) donc il sur-représente les plaintes détaillées. (3) Les applications de mise en service (Enphase, SolarEdge Go, Victron, Fronius, SMA) ne sont pas des outils de conception : elles servent à lire ce que les installateurs attendent d'une appli de chantier. (4) Stack Exchange est dominé par des bricoleurs ; les questions « combien de panneaux / quelle section » restent un bon signal de ce qu'un non-ingénieur ne sait pas calculer.

### 3.1 Capacités vues mais NON proposées, et pourquoi

- Modèle thermique avec température de cellule mesurée / inertie (SAM 106, 380 ; pvlib 1080) : Faiman + NOCT suffisent à un installateur marocain, valeur faible.
- Pertes par la neige (pvlib 2044, 1246 ; SAM 477) : rare hors Atlas ; calcul de charge de neige sur structure exclu.
- Prévision de production, amortissement, limites d'API (ha-solcast-solar, forecast_solar, emhass) : suivi d'exploitation et donnée payante, hors conception.
- Tarifs, rachat, TOU, crédits d'impôt, TRI (SAM, REopt, emhass) : argent calculé dans le module de conception, exclu.
- Trackers (pvlib 1694, 1471 ; ssc 457 ; pvfactors 104, 123 ; bifacial_radiance 179) : exclus.
- Séries sous-horaires 5 minutes (SAM 185 ; pysam 88) : hors décision.
- Compatibilité de paquets Python / ARM / Linux, intégration continue, licences : développement des bibliothèques, pas une capacité d'installateur.
- Charges pilotables VE / pompe à chaleur (emhass 789, 539, 278) : D-RES-2710 (aucune couche ajoutée pour un VE déjà possédé).
- Règle des 120 % du tableau (Stack Exchange, 7 questions) : norme américaine, sans objet au Maroc ; un équivalent marocain = « profil de distributeur » (voir les propositions).
