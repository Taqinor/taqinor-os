## Méthode des courses (lot 2, runner GitHub, run 43541855205)

- **Course réelle à deux connexions.** Le shell Django (seconde connexion Postgres, « le collègue ») ouvre une
  transaction et pose un verrou : ligne (`select_for_update`), table (`LOCK TABLE … SHARE ROW EXCLUSIVE` pour
  ACNC44 op neuve et ACNC47) ou verrou consultatif du lot (ACNC45). Les deux gestes partent (deux `page.request`
  en parallèle, ou deux clics à l'écran). L'étape n'avance que lorsque les DEUX requêtes sont vues bloquées
  ensemble dans `pg_stat_activity` (`wait_event_type = 'Lock'`). Le verrou est ensuite relâché, les deux gestes
  reprennent ensemble et la base est relue (un objet, un mouvement, un paiement, un envoi Celery dans Redis).
- **Écriture croisée (ACNC25, ACNC41).** Une seule requête attend, sur son `UPDATE` (relevé dans
  `pg_stat_activity` : sa lecture `get_object()` est déjà faite). Le collègue commite la transition pendant
  l'attente. La ligne relue garde la transition et le champ du PATCH/PUT.
- **Workers.** gunicorn est lancé avec `--workers 6 --worker-class sync`. La ligne « Workers gunicorn : N
  processus » du workflow est CASSÉE (0 au run 1, 8 au run 3 en comptant `/proc/*/cmdline`) et n'est PAS la
  preuve. La preuve du parallélisme, c'est que deux requêtes étaient bloquées en même temps dans Postgres :
  une course servie l'une après l'autre n'y passerait jamais.
