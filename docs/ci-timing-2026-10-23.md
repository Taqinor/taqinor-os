# Temps du gate PR `ci.yml` — mesures du 23/10/2026 et plan « sous 5 min »

Objectif fondateur : le gate PR de `.github/workflows/ci.yml` sous 5 minutes de
mur pour une PR backend + frontend, avec les mêmes garanties (mêmes tests, gardes
et fuzz ; les six checks requis gardent leur nom ; rien ne devient consultatif ;
`merge_group` complet).

Toutes les durées viennent de `gh run view <id> --json jobs` (début/fin de job,
minutes) et des journaux de job (`gh api repos/Taqinor/taqinor-os/actions/jobs/<id>/logs`).

### 1.1 Le chemin critique n'est pas un job : c'est la FILE

L'organisation est sur le plan **GitHub Free** (`gh api orgs/Taqinor` →
`plan.name = free`) : **20 jobs simultanés pour toute l'organisation**, runners
publics à 4 vCPU. Un run backend + frontend lance aujourd'hui **27 jobs de
travail** dans la même vague (8 shards backend + 8 tranches fuzz + 4 vitest +
2 e2e + stage-names + lint-fast + openapi + fe-static + web), alors que l'en-tête
du fichier (bloc CRÉNEAUX) budgétait 18 : les 8 tranches `api-fuzz-pr` (CI #997,
14/10) sont arrivées après ce calcul. Résultat mesuré : des jobs démarrent 8 à
17 minutes après la création du run (colonne « file max »), alors qu'aucun job
ne dure plus de 9,3 min.

**Plancher physique** : 137 runner-min / 20 créneaux = **6,9 min**, même avec un
remplissage parfait et AUCUN autre run de l'organisation en parallèle. Le
« sous 5 min » exige donc de couper le CALCUL total, pas seulement de le
réordonner — à moins de ≤ ~85 runner-min et ≤ 20 jobs par vague.

### 1.3 Défaut trouvé en passant (chemin « miss » du cache de base de test)

`.github/actions/backend-env/action.yml`, étape de clé de repli : la ligne
`git fetch … 2>&1 \n && git rev-parse …` portait un `\n` LITTÉRAL. Bash le lit
comme un argument `n` (refspec inexistante) : le fetch échoue toujours, et la clé
exacte du dump de `main` n'est jamais proposée à `restore-keys`. Sans effet sur
le chemin « hit » mesuré ici ; sur une PR qui ajoute une migration, le repli
tombe sur le dump le plus récent de n'importe quelle branche, que le garde de
manifeste peut refuser (reconstruction à froid). Corrigé dans cette PR.

## 3. Pourquoi « sous 5 min » n'est pas atteignable sur le plan actuel

Pour 5 min de mur il faut (a) que CHAQUE lane tienne en ~4,3 min mise en place
comprise (≈ 0,5 min de `changes`/`ci-image-check` + 1 saut d'attribution), et
(b) que la somme des lanes tienne dans 20 créneaux × ~4,5 min ≈ 90 runner-min,
SANS aucun autre run de l'organisation.

- Backend : ~2 418 s de mur `--parallel 4` au total (table recalée) + ~70 s de
  mise en place par lane → ≥ 14 lanes pour tenir 4,3 min (≈ 60 runner-min).
- Vitest : ~4 250 s de CPU cumulé, 4 lanes à ~5 min aujourd'hui → 6 lanes.
- e2e : 2 lanes à 4,3-4,8 min (103 s de mise en place + 161 s de specs).
- `stage-names` 3,2-4,5 min, `backend-lint-fast` 2-3, `backend-openapi` 2,5,
  `frontend-static` 2,3.
- Fuzz PR : 8 tranches fixes dès qu'un paquet d'API change (itération 3), 4,3 à
  8,4 min chacune selon la portée.

Total pour une PR qui touche une app ≈ 14 + 6 + 2 + 4 + 8 = **34 jobs,
~120 runner-min** : au-dessus des deux plafonds à la fois. Et la variance des runners publics (même lane : 331 s puis
466 s ; un runner Vitest à 2× le CPU cumulé) interdit toute garantie à 5 min
même quand la moyenne y est.

## 4. Questions au fondateur (rien n'est décidé ici)

1. **Runners payants plus gros** (plan Team + facturation à la minute des
   « larger runners ») : c'est le seul levier qui passe sous 5 min à volume de
   tests constant. Ordre de grandeur à 16 vCPU : backend en 4 lanes
   `--parallel 16` ≈ 2,6 min de tests + 1,2 min de mise en place, Vitest en 2
   lanes ≈ 3 min, `stage-names` ≈ 1,5 min ; ~15 jobs au lieu de 28. Coût : à
   chiffrer sur la grille GitHub en vigueur (≈ 25 min de runner 16 vCPU par run,
   ×2 avec le run de la merge queue). Faut-il lancer un essai chiffré ?
2. **La merge queue re-joue tout** (`merge_group`, run 40034106320 : 12,4 min
   réels, 11,8 sans file). GitHub ne permet pas de réutiliser les checks de la
   PR. Option possible : sauter les jobs lourds du `merge_group` quand l'arbre du
   commit de groupe est IDENTIQUE à celui d'un run PR vert (PR à jour avec
   `main`, groupe d'une seule PR). Cela change ce que la file re-joue : à
   décider par toi.
3. **Les workflows longs affament la CI des PR.** Mesuré pendant ce travail :
   `api-fuzz-full` (poussé depuis `claude/api-fuzz-drain`) tenait 16 des 20
   créneaux pendant > 75 min, et un `Release verify (full suite)` lancé à la
   main tournait depuis 2 h 20 ; quatre PR Dependabot lançaient chacune une CI
   complète. Un `strategy.max-parallel` (par ex. 6) sur ces matrices, et des PR
   Dependabot groupées (`groups:`) hors des heures de travail, rendraient des
   créneaux aux PR. Ces fichiers ne sont pas `ci.yml` : à décider par toi.

Base, détail du travail : shards backend 176 / 198 / 203 / **408 (série)** /
455 / 195 / 317 / 302 s de tests ; vitest 331 / 193 / 200 / 314 s ; Schemathesis
(portée ventes) 34-91 s par tranche derrière ~2,5 min de mise en place chacune.
Variance runner à runner : la même lane 4 (mêmes modules) a mesuré 331 s puis
455 s sur deux runs verts.

Décisions :

1. **Ceinture `--parallel 1` retirée** (shards backend). Justification en
   commentaire dans `ci.yml` : `max_locks_per_transaction=2048` est vérifié par
   `backend-env` (échec franc), 4 purges ≈ 18 000 verrous sur 204 800.
2. **Vitest `--maxWorkers=4`** (défaut vCPU − 1 = 3).
3. **Schemathesis `--workers 4`**, gunicorn 3 → 4 workers.
4. **Portée du fuzz calculée une fois par `changes`** (`fuzz_owners`) : matrice
   sautée sans paquet d'API (au lieu de 8 runners verts à vide), checkout
   superficiel dans les tranches.
5. **ADEP12 + ADEP13 partagent une trace** des gardes `backend-lint-fast`
   (`stage-names` rejouait tout ce job deux fois sous sonde).
6. **`backend-env`** : `\n` littéral corrigé (§1.3).
